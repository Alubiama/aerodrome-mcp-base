# Collect: reuse versus build decision — 2026-09-27

## Recommendation

ADAPT existing SDKs and deployed protocols; keep Collect's basket-selection, net-value comparison, transparent permissions and Base-oriented interface. HOLD a bespoke aggregation engine/new funds-holding router. The preceding bug audit checked local reuse, not a complete external prior-art survey; this separate bounded review closes part of that gap.

Continuing a small product-layer experiment is justified by the user's real dust-balance episode. Market demand, willingness to pay, economical execution at sub-dollar amounts and guaranteed Base rewards are not established.

## Smallest next test

Before building another route engine, evaluate an Enso quote-only spike for synthetic Base AERO + WETH -> USDC, plus one unrouteable token control. Inputs must have exact amounts; record provider fees, minimum output, spender, recipient, approval/reset count, total estimated Base fees and normal EOA strategy. Independent calldata review and fork simulation must show exact selected debits, minimum USDC, no unintended recipient and full swap rollback. Compare with the existing Aerodrome baseline. A single basket swap can still require prior approval transactions; do not advertise one confirmation.

Admission gates: current API key/plan terms and budget must be established before a real Enso request; do not search saved secrets or create a subscription. If Enso cannot support a normal EOA basket, keep it as reference and evaluate LI.FI for route coverage separately. Do not glue independently returned router calldata into Universal Router commands without proving allowance/payer/recipient compatibility.

Pass: real supported basket, inspectable permitted transaction, demonstrable after-fee utility and compatible approvals. Fail: API unavailable, unsupported inputs, opaque/incompatible spender/calls, excessive costs or required account upgrade. A failure revises the provider choice, not the safety gate.

## Method / evidence receipt

Reinvention-prevention trigger: a real SDK/API/deployed-protocol versus custom-engine choice. Search coverage: official SDK docs, repository licenses/source and a bounded search for existing dust products. This is not an exhaustive ecosystem survey. Decision delta: Enso enters first quote-only evaluation; Odos API leaves the primary plan; generic wallet/routing mechanics should be reused while Collect retains its product-specific basket logic. Remaining unknowns are provider integration, economics, exact licenses at pinned refs and installed-wallet behavior.

Quality gate: object_type architecture; verdict proceed-with-guards for a small reuse spike, defer custom router production. Gate findings: API/EOA compatibility and fees are unverified. Qualitative rubric /5: intent 5, scope 4, usefulness 4, risk 3, uncertainty 5, non-duplication 5, actionability 4, leverage 4. Profile: small adapters preserve the current UI and limit blast radius. Overlap is high for generic routing/connection, lower for basket choice.
